# Beauty Trainer

Персональний full-stack тренажер знань про професійний догляд за волоссям. Основний сценарій — активне пригадування, тести, повторення та рекомендації клієнтам, а не просто перегляд каталогу.

## Можливості

- Dashboard: серія навчальних днів, XP, засвоєні продукти, лінійки, черга повторення, слабкі теми й щоденна ціль.
- Каталог **бренд → лінійка → продукт**, пошук і шість фільтрів: бренд, лінійка, тип волосся, категорія, призначення, перевага.
- Сторінки лінійки й продукту з описами, складниками, перевагами та прогресом.
- Сесії до 10 запитань: розпізнавання лінійки, тип волосся/потреба, продукт, перевага, зворотне пригадування, клієнтська ситуація, правда/неправда.
- Ще шість форматів: продукт за фото, зіставлення пар, кілька правильних відповідей, спосіб застосування, пошук помилки та вибір продукту з поясненням.
- Навчальні картки й окремий тест кожної лінійки; загальне тренування охоплює весь каталог.
- Три життя на тест: після третьої помилки автоматично відкриваються результати. У складених завданнях відповідь перевіряється цілком кнопкою «Перевірити» — максимум одне втрачене життя за завдання.
- Миттєве пояснення відповіді, 10 XP за правильну відповідь, підсумок із сильними/слабкими темами й продуктами для повторення.
- Окрема історія засвоєння брендів, лінійок і продуктів; автоматичне планування повторення.
- Слабкі теми та пари продуктів, які користувач плутає.
- CRUD-форми брендів, лінійок і продуктів; JSON-імпорт з перевіркою структури, ID та батьківських зв’язків; JSON-експорт.
- Адаптивний інтерфейс і світла/темна тема.
- Українська мова інтерфейсу, запитань, пояснень, повідомлень валідації та демонстраційних навчальних матеріалів. Назви брендів, лінійок і продуктів збережено в оригіналі; дати й числа мають український формат.

## Стек і архітектура

React 19, strict TypeScript, Vite, Tailwind CSS 4, React Router, Lucide; Cloudflare Worker і D1; Zod для спільної валідації.

```text
src/
  components/       повторно використовувані картки, індикатори й UI
  pages/            dashboard, каталог, тренування, прогрес, адмін
  hooks/            спільне завантаження стану
  services/         клієнт REST API
shared/
  schema.ts         схеми JSON та типи
  learning.ts       генерація запитань і правила повторення
worker/
  index.ts          REST-маршрути, оцінювання, відповіді з помилками
  db/catalog.ts     читання та пакетний запис нормалізованого каталогу
migrations/         SQL-міграції D1
data/products.json  каталог, імпортований із Notion
scripts/seed.ts     перевірка JSON та генерація SQL
tests/              модульні та браузерні інтеграційні тести
```

Frontend звертається до `/api`. Для production один Worker обслуговує REST API та зібрані статичні файли React. Такий варіант не потребує другого сервісу, CORS чи окремого розгортання frontend.

## Локальний запуск

Потрібні Node.js **22.20 або новіший у гілці 22**, npm та Chrome для браузерних тестів. Cloudflare-акаунт не потрібен для локальної роботи.

```sh
npm ci
npm run build
npm run db:migrate
npm run db:seed
```

Перша збірка створює `dist`, необхідний для налаштування Worker Assets.

У першому терміналі:

```sh
npm run dev:api
```

У другому:

```sh
npm run dev
```

Відкрийте **http://127.0.0.1:5173**. Vite проксіює `/api` до Worker на порту 8787. Після збірки production-версія також доступна локально на **http://127.0.0.1:8787**.

Дані зберігаються у `.wrangler/state` та залишаються після перезапуску. Міграції повторно не застосовуються. Seed додає/оновлює записи з відповідними ID, не видаляючи інші продукти та не скидаючи навчальний прогрес.

Для оновлення вже наявної англомовної демонстраційної бази виконайте `npm run db:migrate`. Міграція `0002_ukrainian_demo_content.sql` перекладає лише початкові тексти, які не були змінені користувачем. Вона зберігає ID, власні редагування та навчальний прогрес. Повторно запускати seed для перекладу не потрібно. Власні імпортовані тексти відображаються тією мовою, якою їх додано.

`.env.example` описує необов’язковий `VITE_API_URL`. Для стандартного запуску залиште його порожнім: усі запити мають той самий origin. Зовнішній origin без додаткового проксі та CORS-конфігурації не підтримується. Секретні ключі не можна додавати у змінні з префіксом `VITE_`.

## Початкові дані та імпорт

Станом на 2026-09-16 `data/products.json` містить **2 бренди, 36 лінійок і 119 продуктів**: milk_shake — 22 лінійки та 74 продукти, Insight — 14 лінійок та 45 продуктів. Матеріали імпортовано з користувацького експорту Notion у `notion-export/`; це навчальна база, а не незалежно перевірений довідник виробників.

Для Insight є 45 фото продуктів і 9 інструкцій застосування. Для milk_shake є фото лінійок, але немає окремих фото продуктів; фото лінійки не використовується як фото конкретного засобу в тесті. Частина складників milk_shake перенесена з опису лінійки, тому її не слід трактувати як підтверджений склад кожного продукту. Запитання про складники не реалізовано; ідею відкладено в `IDEAS.md`.

JSON верхнього рівня має масиви `brands`, `lines`, `products`. Повний приклад — `data/products.json`, або кнопка **Export JSON** в адмінці.

| Об’єкт  | Обов’язкові поля                                                                                                   |
| ------- | ------------------------------------------------------------------------------------------------------------------ |
| Brand   | `id`, `name`, `description`                                                                                        |
| Line    | `id`, `brand_id`, `name`, `short_description`, `description`, `hair_types`, `purposes`, `benefits`, `keywords`     |
| Product | `id`, `brand_id`, `line_id`, `name`, `category`, `description`, `hair_types`, `purpose`, `benefits`, `ingredients` |

Масиви характеристик містять непорожні рядки. `image` — необов’язкова HTTPS-адреса або локальний шлях `/images/...`; файли зберігаються в `public/images/`. `usage` — необов’язковий текст. ID стабільні, у нижньому регістрі, з цифрами та дефісами. Назви можуть містити будь-яку мову.

1. Відкрийте **Manage products**.
2. Завантажте JSON або вставте текст.
3. Натисніть **Validate JSON**, перегляньте кількість записів та помилки.
4. Натисніть **Import validated data**.

Імпорт доповнює бібліотеку: існуючі ID оновлюються, нові додаються. Файл має включати батьківські бренди й лінійки. Перевіряється також сумісність із уже збереженими товарами; наприклад, не можна перепризначити лінійку іншому бренду й залишити товари зі старим `brand_id`.

Валідний імпорт зберігається однією атомарною D1 batch-транзакцією. Некоректні дані не змінюють базу. Максимальний розмір JSON — 2 MB; для одного API-імпорту дозволено до 40 SQL-операцій після пакетування. Надто великі файли потрібно розділити, залишаючи батьківські об’єкти в кожній частині. Це враховує [ліміти D1](https://developers.cloudflare.com/d1/platform/limits/) без вимоги платного тарифу.

Видалення бренду каскадно видаляє його лінійки й продукти. Видалення лінійки видаляє її продукти. Відповідний прогрес очищається, історичні оцінки та XP зберігаються.

## Навчальна логіка

Запитання створюються з поточного каталогу на сервері, без AI API. Для одного каталогу, стану прогресу, часу та seed результат детермінований. ID сесії є seed, тому нові сесії відрізняються.

Звичайний шлях навчання: оберіть бренд і лінійку → перегляньте картки та пригадайте призначення продуктів → пройдіть тест лінійки → повторіть помилки → повертайтеся до загального тесту й черги повторення. Картки допомагають підготуватися, а відповіді в тестах формують збережений прогрес.

Фото-запитання потребують окремого зображення продукту й альтернатив; запитання про застосування — наявної інструкції. Пари формуються з трьох продуктів однієї лінійки з різними призначеннями. Кілька відповідей перевіряють переваги, прямо зазначені в картці, а не заперечують інші властивості. Пошук помилки перевіряє суперечність категорії продукту; вибір із поясненням — одночасно продукт і перевагу з його картки. Нові формати пропускаються, якщо матеріалів недостатньо. Не кожна сесія містить усі 13 форматів.

Складені відповіді передаються як JSON-масив у рядку `answer`: набір варіантів для кількох відповідей (порядок неважливий), призначення в порядку `items` для пар або `[продукт, пояснення]`. Сервер перевіряє допустимі варіанти та повноту пар, оцінює все завдання один раз і зберігає читабельну відповідь в історії. Часткових XP немає. Старі сесії з одним варіантом залишаються сумісними.

Черговість: прострочені повторення → слабкі продукти → слабкі лінійки → нові теми → інші теми. У межах пріоритету балансуються формати й теми. За недостатньої кількості різних відповідей сесія може бути коротшою за 10 запитань. Режим слабких тем не підставляє нові теми, якщо слабких ще немає.

Правильні відповіді та пояснення залишаються на сервері до оцінювання. Клієнт не задає правильність, XP або mastery. Унікальний ключ `(session_id, question_id)` і умовні операції в одній транзакції запобігають повторному нарахуванню під час повторних чи одночасних запитів.

- Правильно: **+15 mastery**, **+10 XP**.
- Неправильно: **−20 mastery**, повторення через **10 хвилин**, 0 XP.
- Mastery обмежено діапазоном **0–100**.

| Mastery після правильної відповіді | Наступне повторення |
| ---------------------------------- | ------------------- |
| 0–20                               | через 4 години      |
| 21–40                              | через 1 день        |
| 41–60                              | через 3 дні         |
| 61–80                              | через 7 днів        |
| 81–99                              | через 14 днів       |
| 100                                | через 30 днів       |

Продукт вважається засвоєним від **80%**, слабка тема — нижче **60%** серед уже вивчених. Підрахунок серії та щоденних відповідей використовує **UTC**, щоденна ціль — 10 запитань. Черга на dashboard рахує теми лінійок і продуктів, а не дублюючі записи брендів. Вихід зі сторінки тренування завершує поточний UI-сеанс; уже надані відповіді збережено.

### Редагування текстів Insight

У `data/insight-copy.json` зберігаються відредаговані короткі описи лінійок
і переваги продуктів. Імпортер застосовує їх за стабільними ID після читання
Notion, тому повторний імпорт не повертає уривки речень. Для оновлення лише
локальних даних без перекодування фото: `npx tsx scripts/import-notion.ts Insight --write-data`.
Оригінальні Markdown-файли залишаються джерелом повних описів.

Назви двох продуктів Clarifying уточнено за фото `image 52.png` (шампунь)
та `image 53.png` (догляд із піпеткою), описами й інструкцією «Не змивати»:
«Очищувальний шампунь» та «Очищувальний лосьйон». ID залишено незмінними,
щоб зберегти посилання та навчальний прогрес.

Кожне нове тренування починається з трьох життів. Правильна відповідь
зберігає життя, помилка забирає одне. Після третьої помилки автоматично
відкривається підсумок «Тест не складено» з поясненнями помилок; наступні
відповіді сервер відхиляє з HTTP 409. Повторне надсилання вже збереженої
відповіді повертає початковий результат без додаткових списань чи XP.
Тест складено, якщо всі запитання пройдено з хоча б одним життям.
Нове проходження відновлює три життя; попередні XP та історія зберігаються.
Біля лічильника запитань показано три сердечка; на телефоні — кількість і одне
сердечко. Якщо сервер уже завершив сесію, інтерфейс відкриває її збережені
результати після відповіді `SESSION_EXHAUSTED`, замість залишатися на запитанні.

На сторінці лінійки також доступні «Вивчити картки» (`/lines/<id>/cards`):
спочатку назва продукту й запитання для пригадування, після відкриття —
призначення, типи волосся, переваги та спосіб застосування, якщо він є.
Позначки «Пам’ятаю» / «Ще повторити» формують підсумок поточного кола;
можна повторити складні картки або перейти до тесту лінійки. Ця самооцінка
зберігається лише до виходу зі сторінки та не нараховує XP.

На сторінці лінійки кнопка «Пройти тест лінійки» відкриває `/training?line=<id>`.
Запит створення сесії приймає необов’язковий `lineId`, наприклад
`{ "mode": "all", "lineId": "curl-passion" }`. Запитання й варіанти продуктів
обмежені цією серією; розпізнавання назви лінійки пропускається. Якщо різних
варіантів недостатньо, сесія містить менше ніж 10 запитань. Невідомий `lineId`
повертає 404. Без `lineId` загальний тест працює як раніше. XP та прогрес
зберігаються у спільній історії навчання.

## REST API

| Метод  | Шлях                                                     | Призначення                                  |
| ------ | -------------------------------------------------------- | -------------------------------------------- |
| GET    | `/api/catalog`                                           | каталог із характеристиками                  |
| GET    | `/api/progress`                                          | mastery, історія, XP, streak                 |
| POST   | `/api/brands`, `/api/lines`, `/api/products`             | створення об’єкта                            |
| PUT    | `/api/brands/:id`, `/api/lines/:id`, `/api/products/:id` | редагування зі збереженням ID                |
| DELETE | ті самі шляхи з `:id`                                    | видалення та каскад                          |
| POST   | `/api/import`                                            | перевірений JSON-каталог                     |
| POST   | `/api/sessions`                                          | `{ "mode": "all" }` або `{ "mode": "weak" }` |
| POST   | `/api/sessions/:id/answers`                              | `{ "questionId": "…", "answer": "…" }`       |

Помилки мають JSON-формат `{ "error": "…" }` та відповідний HTTP-код.

У MVP один користувач `local`, без авторизації, як передбачено вимогами. Його ID визначається в `worker/index.ts`; таблиці прогресу, історії та сесій уже містять `user_id`, щоб пізніше додати авторизований контекст. Наразі кожен відвідувач розгорнутого застосунку використовує спільний прогрес та може змінювати каталог — врахуйте це при виборі доступності deployment.

## Перевірки

```sh
npm run typecheck
npm run lint
npm test
npm run build
npm run test:e2e
```

Модульні тести перевіряють валідацію, детермінізм, формати, пріоритети, межі mastery та інтервали. Playwright запускає зібраний Worker на **8788** з окремою базою **`.wrangler/e2e`** і перевіряє браузерний навчальний цикл, каталог, CRUD, імпорт, мобільну ширину, тему, помилки API й повторні відповіді. Основна локальна база не змінюється. Браузерні тести додають відповіді у свою ізольовану базу; їх можна запускати повторно.

Локально Playwright використовує встановлений Chrome. У CI використовується Chromium:

```sh
npx playwright install --with-deps chromium
```

Для форматування: `npm run format`; перевірка: `npm run format:check`.

Актуальний склад перевірок міститься в `tests/`; результати залежать від поточного запуску. Браузерні знімки зберігаються в `test-results/`.

## Розгортання Cloudflare Workers + D1

Налаштовано **Workers Static Assets**: це production-варіант для цього MVP, без окремого Cloudflare Pages-проєкту.

```sh
npx wrangler login
npx wrangler d1 create beauty-trainer
```

Для нового розгортання скопіюйте отриманий `database_id` в `wrangler.jsonc`. У репозиторії вже налаштовано наявну D1; її не потрібно створювати повторно. Потім:

```sh
npx wrangler d1 migrations apply beauty-trainer --remote
npm run seed:generate
npx wrangler d1 execute beauty-trainer --remote --file=data/seed.sql
npm run deploy
```

`npm run deploy` перевіряє TypeScript, збирає frontend і публікує Worker з assets. URL видає Wrangler. Наступні зміни frontend/backend публікуються тією ж командою; нові міграції потрібно застосовувати перед deployment, не редагуючи вже застосовані SQL-файли.

Офіційні інструкції: [D1 migrations](https://developers.cloudflare.com/d1/reference/migrations/), [Worker configuration](https://developers.cloudflare.com/workers/wrangler/configuration/), [Vite build](https://vite.dev/guide/build).

Створіть репозиторій GitHub і додайте ці файли стандартним Git-процесом. `.gitignore` виключає локальні бази, секрети, build та тестові артефакти. Доданий `.github/workflows/ci.yml` виконує перевірки для push і pull request.

Для автоматичного deployment можна підключити GitHub-репозиторій через **Cloudflare Workers Builds**: build command `npm run build`, deploy command `npx wrangler deploy`. Спершу створіть D1, внесіть правильний ID і застосуйте remote-міграції. Початкові дані не імпортуються автоматично при кожній публікації.

Застосунок не потребує OpenAI, інших AI API, платних API-ключів чи зовнішнього сервісу автентифікації.
